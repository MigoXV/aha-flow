# Realtime 服务端整改清单与验收条件

记录日期：2026-11-05。面向语音服务端维护者，以 OpenAI Realtime 转写协议为兼容基线。

## 结论与范围

本次已复现的首要问题是：默认 VAD 模式下，静音音频的显式提交没有标准成功或失败响应，客户端因此等满收尾超时。托盘图标立即隐藏只是客户端的交互修复，进程仍可能等待 30 秒，不能视为服务端问题已经解决。

另已观察到越界 VAD 阈值被接受，以及部分配置的处理结果无法从响应确认。以下区分“已复现的问题”“整改要求”和“待验证项目”；不能把待验证项目直接算作服务端已存在的缺陷。

测试服务为用户指定的局域网 HTTPS 引擎，模型为 `default-audio`。未检查服务端源码，不能据此确定具体内部模块或实现原因。未使用真实录音或麦克风；音频样本为内存生成的 1 秒静音，24 kHz、单声道 PCM16LE，分 10 个 100 ms 包按实时节奏发送。测试允许该开发服务的自签名证书。耗时均为单次观测，不是性能基准。

## 已复现证据

| 检查 | 观测结果 | 能得出的结论 |
| --- | --- | --- |
| `GET /v1/models` | HTTP 200，约 28 ms | 该次模型列表请求没有长时间等待 |
| 客户端 `--check-session` | 约 114 ms 成功 | 该次连接和会话初始化较快 |
| 默认 VAD，静音回放后提交 | 客户端总耗时约 31.2 秒，以最终结果等待超时退出 | 收尾路径未闭合 |
| 默认 VAD，开启 AHA 扩展的独立协议探针 | 提交后收到处理到 1000 ms 的 `x_aha.vad.progress`，最后 `final: true`；6 秒观察窗内没有提交确认、转写完成或标准错误 | 私有进度事件没有完成标准提交闭环 |
| 默认 VAD，不带 `x_aha=v1` | 6 秒观察窗内同样未收到提交确认、转写完成或标准错误 | 此问题也影响仅使用标准协议的客户端 |
| 关闭 VAD，手动提交相同静音 | 会话起约 1032 ms 收到 `input_audio_buffer.committed`，约 1202 ms 收到空字符串的最终转写 | 手动模式能完成同一样本的闭环 |
| 合法 server VAD 参数 | `threshold=0.65`、`prefix_padding_ms=450`、`silence_duration_ms=800` 被接受并回显 | 配置入口接受这些值；未验证音频效果 |
| semantic VAD 参数 | `type=semantic_vad`、`eagerness=high` 被接受并回显 | 未证明语义检测或积极程度实际生效 |
| 越界阈值 | `threshold=2.0` 得到 `session.updated`，有效配置仍为 `2.0` | 参数范围校验或有效配置报告存在问题 |
| 近场降噪 | 请求 `noise_reduction: {"type":"near_field"}` 得到 `session.updated`，但有效输入配置没有此字段，也没有错误 | 无法判断启用、忽略或不支持；不能断言降噪未实现 |
| 人造未知字段 | `audio.input.nonexistent_test_option=true` 被接受，但未回显 | 当前表现为忽略未知字段；是否符合目标兼容策略需要明确 |

## P0：修复 VAD 模式下的显式提交闭环

### 复现步骤

1. 连接 `/v1/realtime?intent=transcription`。分别覆盖带与不带 `x_aha=v1` 的连接。
2. 等待 `session.created`，发送以下配置，等待 `session.updated`：

```json
{
  "type": "session.update",
  "session": {
    "type": "transcription",
    "audio": {
      "input": {
        "format": {"type": "audio/pcm", "rate": 24000},
        "transcription": {"model": "default-audio"}
      }
    }
  }
}
```

3. 每 100 ms 发送一次 `input_audio_buffer.append`，其 `audio` 为 4800 字节零值 PCM 的 Base64，共 10 次。
4. 发送 `{"type":"input_audio_buffer.commit","event_id":"commit-silence-1"}`，保持连接观察返回事件。本次原探针没有附加客户端 `event_id`；此处增加该字段用于整改后的请求关联验收。
5. 对照测试：将 `audio.input.turn_detection` 显式设为 `null`，重复上述步骤。

### 服务端修改要求

- 显式提交必须有可判断的结果。提交成功时返回标准 `input_audio_buffer.committed`，为该轮转写提供最终完成或失败事件。
- 静音、有音频字节但没有检测到语音、真正的空缓冲区，需要分别处理。若成功建立转写项，可以用空转写表示没有识别到文字；若拒绝提交，返回明确的标准 `error`。不得静默吞掉请求。
- 若 VAD 已自动提交，随后的显式提交实际遇到空缓冲区，应按空提交处理并返回错误，而不是让客户端无限等待，也不能重复创建同一轮。
- 标准客户端忽略所有 `x_aha.*` 消息后仍须正常完成。私有的 `final: true` 只报告其定义的阶段完成，不能替代标准转写终态。

官方对提交的定义包含成功返回 `input_audio_buffer.committed`、空缓冲区返回错误；服务端事件定义了转写完成和失败消息。依据：[客户端事件参考](https://developers.openai.com/api/reference/resources/realtime/client-events)、[服务端事件参考](https://developers.openai.com/api/reference/resources/realtime/server-events)。

### 验收条件

- 上述静音用例，在默认 VAD 和手动模式、带与不带 AHA 扩展时，均收到标准成功闭环或明确错误。
- 建议为该轻载局域网静音回归用例设定“提交后 2 秒内完成或明确失败”的工程目标；这是本项目建议的验收预算，并非 OpenAI 的服务承诺。
- 成功响应中的提交项与转写终态使用同一个 `item_id`，每个已接受转写项最终有且只有一个成功或失败终态。
- 实际 `--replay-pcm` 入口完成成功静音转写时正常退出；拒绝提交时及时报告错误，不以客户端 30 秒超时作为正常结束方式。
- 有真实语音的轮次继续等待最终文字，不因收到 VAD 进度结束而提前丢弃结果。

## P1：校验参数范围，拒绝无效配置

### 已复现

```json
{"turn_detection":{"type":"server_vad","threshold":2.0}}
```

该输入被接受，有效配置回显 `threshold=2.0`。官方定义的阈值范围是 0 到 1。依据：[turn_detection 字段定义](https://developers.openai.com/api/reference/resources/realtime/client-events)。

### 服务端修改要求与验收

- 为配置建立统一的类型、枚举和范围校验；模型不支持的参数应明确拒绝。
- `threshold=2.0`、负值、错误类型应收到标准错误，指出 `session.audio.input.turn_detection.threshold`。不要接受后交给底层算法产生不可预测行为。
- 失败配置不能污染已建立会话；修正后再次更新应能成功。原子性与连接可继续使用应作为回归要求。
- 合法阈值应出现在有效配置中；实际音频效果另行验证。
- 其他 VAD 数值、`eagerness`、降噪类型与强度，也应覆盖边界和无效枚举；本次未全面测试这些非法输入，不能宣称它们都存在同类问题。

## P1：让配置结果可判断，区分支持、拒绝和默认值

### 已观察到的歧义

请求近场降噪后响应成功，但有效配置未包含降噪字段；关闭 VAD 的手动模式响应也没有显式回显 `turn_detection: null`。前者无法确认处理结果，后者要求客户端从缺省字段推断关闭状态。

### 服务端修改要求与验收

- 在 `session.updated` 中报告实际生效的配置。近场降噪若支持，应回显实际设置；若不支持，应返回带参数路径的错误。不要仅凭成功响应让使用者以为已生效。
- 关闭 VAD 应清晰报告关闭状态；省略字段、显式 `null` 和显式对象的更新语义需保持一致。
- 模型能力限制由服务端校验并解释；用户移除不支持的可选字段后，应能恢复运行。
- 对未知字段制定与目标 OpenAI 接口一致的策略，并通过对照测试确认。当前“接受并省略”仅是实测行为，不能据此认定全部未知字段都必须报错。
- 错误应包含可读原因、参数路径，并在请求提供 `event_id` 时关联该请求。本次尚未验证错误关联的实际实现。

官方说明 `session.updated` 展示完整有效配置。依据：[session.update 定义](https://developers.openai.com/api/reference/resources/realtime/client-events)。

## P1：补齐服务端协议回归与收尾观测

以下为落实前述整改的工程建议，未检查服务端当前是否已有这些设施。

| 回归场景 | 检查重点 |
| --- | --- |
| 空缓冲区、纯静音、短于最低时长的音频 | 明确拒绝或成功；不静默挂起 |
| VAD 自动提交后立即显式提交 | 不重复转写；空提交明确反馈 |
| 讲话中停止、尾部静音停止 | 最后一轮有终态，不丢尾字 |
| 连续多轮、提交后立即追加下一轮 | 项目关联正确，不吞掉后续音频 |
| ASR 失败、内部超时、客户端断连 | 及时失败，任务和会话资源回收 |
| AHA 扩展开关 | 标准事件闭环一致，扩展仅增加信息 |
| 无效参数后修正重试 | 错误可定位，后续合法配置可用 |

建议按会话和 `item_id` 记录提交接收、VAD 完成、ASR 排队/执行、最终事件发送时间，并统计提交到终态的耗时和未闭合项数。这样才能区分 VAD、排队、推理和事件发送中的等待；本次无法仅凭客户端证据确定服务端内部耗时分布。

## 尚未验证的兼容能力

- `semantic_vad` 的真实断句效果，以及 `low/medium/high/auto` 是否实际改变行为。
- `threshold`、前置保留、静音时长是否改变实际检测结果；配置回显不等于算法生效。
- 近场/远场降噪与强度的真实音频效果。
- 其他模型的能力限制、语言、提示词、关键词、延迟、概率输出，以及更新失败后的恢复。
- 并发、长会话、真实语音尾部、ASR 内部故障和资源回收。
- 与官方服务相同输入下的逐事件对照。本次没有再次调用官方付费 API；协议依据是官方文档，本地官方接口的历史实测另见 [官方验证记录](realtime-validation.md)。

整改顺序建议：先修提交闭环，再补范围校验与有效配置报告，随后用真实语音和多模型回归验证行为兼容。客户端保留超时与数据保存保护；服务端正常完成应由标准事件驱动，不能依赖隐藏图标或缩短客户端等待时间掩盖协议缺口。
